## 新增「自助创建班级」功能

### 需求背景
马老师要新增一个班级。项目原本**没有创建班级的功能**（搜遍 `createClass`/`addClass` 都没有），只能在云开发控制台手动往 `classes` 集合加记录。

马老师明确澄清：**不做多班级管理改造**。保持「一个教师账号 = 一个班级」的模型，同一个老师用不同教师账号登录不同班级即可，不需要一个账号切换多个班。

### 实现内容

#### 1. 新增 `createClass` 云函数
- 路径：`cloudfunctions/createClass/`
- 逻辑：接收 `className` → 自动生成双密钥 → 写入 `classes` 集合
- 密钥规则（与 `importStudents` 的 genKey 风格统一）：
  - `teacherKey` = `T` + 5 位随机码（教师登录用）
  - `studentKey` = `S` + 5 位随机码（学生加入用）
  - 字符集 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（剔除易混淆的 I / O / 0 / 1）
- 唯一性校验：生成后查 `classes` 集合 `count()` 确认无重复，最多重试 20 次
- 返回 `classInfo`（_id / name / teacherKey / studentKey）+ `nameDuplicated` 标记（同名班级仅提示，不阻断）

#### 2. 登录页改造（login.js / login.wxml / login.wxss）
- 底部新增「还没有班级？注册一个新班级」入口
- 点击弹出深色弹窗（配合登录页紫色主题 #6c63ff），两种状态：
  - 状态一：输入班级名称 → 点「创建」
  - 状态二：创建成功 → 展示双密钥（各带复制按钮）+ 「进入新班级」按钮
- 「进入新班级」复用现有 `_teacherLogin()`，用新 teacherKey 直接登录进教师端，形成闭环
- 弹窗样式写在 login.wxss 内（app.wxss 无全局 modal 样式，各页面自定义）

### 需要上传的云函数
- `createClass`（新增）

### 不需要创建的集合
- `classes` 集合已存在，本次未引入新集合

### 关键结论：班级模型（后续开发需遵守）
- 一个班级 = `classes` 集合一条记录，业务字段只有 `name` / `teacherKey` / `studentKey`（+ 自动 `_id`）
- 教师登录：`where({ teacherKey })` 取第一条
- 学生登录：先用 `studentKey` 找班级 → 再用个人 `studentKey` 找学生

- **一个教师账号对应一个班级**，带多个班就注册多个，各用各的 teacherKey

## Bug 修复：改完密钥就登不进去（两个叠加 Bug）

### 现象（马老师反馈）
修改密钥时弹出"修改错误" → 但教师端页面却显示成了新密钥 → 再改一次提示"重复" → 用新密钥登录却进不去。

### 根因一：写入侧转大写、查询侧没转（导致登录失败）
- `updateClassKeys` 保存时 `normalizeKey()` = `.trim().toUpperCase()`，数据库存的是**大写**
- `login` 云函数查询时**原样** `where({ teacherKey })`，**没有归一化**
- 于是库里是 `LONGYUE7`，老师输入 `longyue7` → 永远查不到 → "教师密钥不正确"
- 而教师端页面用 `getClassData` 的 `doc().get()` 读库原值，显示的是**真实生效的大写值**
  → 所以"页面显示更新了，但登录不了"并不矛盾

**修复**：`login` 云函数加 `normalizeKey` + `findByKey` 双查（先查原值、再查大写），
既支持大小写混输，也不影响历史数据里可能存在的旧小写密钥。学生个人密钥同样双查。

### 根因二：`doc().update()` 返回结构不可靠 → 假失败（导致"报失败却已生效"）
- 代码里判断 `if (!updateRes.updated)` 就返回"更新失败"
- 但**不同调用方式/SDK 版本返回结构不同**：可能是 `{ updated: 1 }`，也可能是 `{ stats: { updated: 1 } }`
- 一旦是后者，`updateRes.updated` 为 undefined → 误判失败 → **返回错误，但数据库其实已经改成功了**
- 这正是"弹修改错误"却"页面显示新密钥"的矛盾来源，也是再改一次时各种"重复/冲突"提示的源头

**修复（关键工程加固）**：**写后读回验证**——不再信任 update 的返回值结构，
写入后重新 `doc().get()` 读一次，以数据库真实值为准判断是否生效：
```js
const verifyRes = await db.collection('classes').doc(classId).get()
if (!verifyRes.data || verifyRes.data[type] !== key) { /* 才算真失败 */ }
```

### 顺带加固
- `updateClassKeys`：本班内 `teacherKey` 与 `studentKey` **不允许相同**（否则学生和老师用同一口令会进错端）
- 前端 `onKeyEditInput`：输入即去空格 + 转大写，做到"输入框看到的 = 库存的 = 登录要输的"
- 前端 `saveKeyEdit`：粘贴绕过输入监听时再归一化一次；确认弹窗提示大写形式

### 教训
1. **归一化规则必须在"写入侧"和"查询侧"成对出现**——只在一侧做，等于埋雷
2. **不要依赖 update 的返回结构判断成功与否**，`doc()` 与 `where()` 返回不一样，SDK 版本也可能变；
   写后读回是最稳的
3. 现象矛盾（"失败了"却"生效了"）时，第一反应应该是**假失败**：操作成功但返回值解析错了

- `updateClassKeys`（**必须传**）

## 新增「删除班级」功能（危险操作，三重安全锁）

### 需求

1. `teacherKey` 必须与班级记录匹配（大小写不敏感，复用 normalizeKey）
2. `confirmName` 必须与该班 `name` 完全一致
3. `students.where({ classId }).count()` 必须为 0，否则返回 `needRemoveStudents: true` 并带上学生数

#### 2. 重写 `deleteStudent` 云函数（重要：原版只清了 2 个集合）

- 挑战记录的两个字段都要清：`challengeHistory` 用 challengerId/targetId，
  `challengeLogs` 用 challengerId/opponentId（学生可能是发起方也可能是被挑战方）
- 同样加了写后读回验证

#### 3. 教师端 `teacher-class` 页面
- 班级信息卡底部新增「⚠️ 危险操作」区 + 「🗑️ 删除班级」按钮

  - 还有学生 → 红色阻断提示，写明还剩几名，删除按钮禁用

  （classId/className/isTeacher/studentInfo）→ reLaunch 回登录页

### 两个关键设计点（避免误删，后续务必保持）

**① 反查历史 studentId 时必须排除"已转到其它班的活跃学生"**
学生被「移出班级」转到别班后，students 里他依然存在但 classId 已变。
若照单全删他的 badgeStatus/weeklyStats，会**误删他在新班级的数据**。
所以加了 `filterOutActiveStudents()`：凡仍在 students 且 classId ≠ 本班的，一律排除。
（前置校验已保证本班无学生，所以仍在库的必然是转到别班的）

**② taskPool 混有全局预置任务**
`where({ classId })` 只会命中本班自定义任务，不会误删公共题库——不能用清空集合的方式。

### 分页删除的通用写法
云函数单次 `get()` 上限 100 条，必须循环分页；`_.in()` 一次别塞太多 ID（50 个一批）：
```js
async function removeWhere(name, where, maxRounds = 100) {
  for (let i = 0; i < maxRounds; i++) {
    const res = await db.collection(name).where(where).limit(100).get()
    if (!res.data || res.data.length === 0) break
    const ids = res.data.map(d => d._id)
    await db.collection(name).where({ _id: _.in(ids) }).remove()
    if (res.data.length < 100) break
  }
}
```
集合不存在时 where().get() 会抛错 → try/catch 返回 error 但**不阻断**其它集合的清理。

## 新增「金币模块」（为未来商城做准备）

### 需求（马老师提出 + 4 项决策）
学生赚金币、教师发金币、学生互赠，未来可接商城卖虚拟道具和装扮。
经确认的决策：
1. **获取途径：暂不自动发放** —— 不挂签到/任务/挑战，只靠教师发放 + 学生互赠
2. **互赠限制：每日限额** —— 每天最多 3 次、累计 20 金币，单次 1-20
3. **教师权限：对公钱包制（关键架构决策）** —— 教师只能从**班级对公钱包**里发，
   钱包额度由 super 管理员定；目前 super 管理**直接改数据库**实现，
   未来再做 super 管理员后台前端（现在不急）
4. **排行榜：加一个金币榜**

### 资金模型（双层账户）
```
super 管理员（手动改库充值）
    ↓ 充值
班级对公钱包 wallets（按 classId，_id = classId）
    ↓ 教师发放 grant / 回收 deduct
学生金币 students.coins
    ↓ 学生互赠（不经过钱包，全班总量不变，只改变分布）
学生金币 students.coins
```
- 教师发放：钱包 -N，学生 +N
- 教师扣除：学生 -N，钱包 +N（回流，不是销毁）
- 学生互赠：点对点，钱包余额不变

### 新增集合（2 个，必须去云控制台创建）
- **`wallets`** 班级对公钱包：`{ _id: classId, classId, balance, totalRecharged, totalGranted, totalRecycled }`
- **`coinLogs`** 金币流水：`{ studentId, classId, amount, balance, type, description, operatorId, operatorName, relatedId, date, createdAt }`
  - `amount` 正=收入、负=支出；`balance` 是变动后余额（对账用）
  - `type` 枚举：`teacher_grant` / `teacher_deduct` / `transfer_out` / `transfer_in` / `shop_purchase`（商城预留）
  - **`date` 字段（YYYYMMDD）是专门为"每日限额"加的**，让限流查询变成一次简单 where

### students 新增字段
- `coins` 当前余额（一律用 `_.inc()` 原子增减）
- `totalCoinsEarned` 累计获得（只增不减，供成就/金币榜用，不受扣除影响）

### 新增云函数（3 个）
| 函数 | 职责 |
|---|---|
| `coinOperation` | action: `grant`/`deduct`/`query`。钱包↔学生转账 + 查钱包余额 |
| `transferCoins` | 学生互赠：同班校验 + 排除自己 + 余额校验 + 每日限额 + 双向流水 + 通知对方 |
| `getCoinLogs` | action: `list`（流水）/ `summary`（余额+今日剩余额度）/ `classList`（全班概览，预留） |

### 三个关键工程决策（后续务必保持）

**① 用 `db.runTransaction` 而不是手动 `startTransaction`**
runTransaction 在并发冲突时**自动回滚重试**，比手写 commit/rollback 可靠。
资金变动（钱包扣减 + 学生到账 + 流水写入）放在同一个事务里，账实必然一致。

**② 业务失败用返回值标记，不要在事务里抛异常**
抛异常会触发无意义的重试，把"余额不足"这种正常业务结果放大成错误。
```js
const r = await db.runTransaction(async (t) => {
  if (余额不足) return { ok: false, reason: '钱包余额不足' }   // 返回而非 throw
  ...
  return { ok: true }
})
if (!r.ok) return { success: false, error: r.reason }
```

**③ 钱包 `_id` 直接用 `classId`（天然防重复创建）**
若按 `where({classId})` 查不到就 add，两个并发请求会建出**两个钱包**，
而 `limit(1)` 不保证稳定排序 → 余额会分散在两个钱包里，教师看到的余额是错的。
用 classId 当主键：并发时后一个主键冲突失败 → catch 后重新读回即可。

### 批量发放的时长控制
每人一个**独立短事务**，而不是一个长事务包所有人：
- 避免长事务超时（云函数默认 3 秒）
- 单个失败不影响其他人，失败明细原样返回给前端（前端提示"成功 N 人，失败 M 人"+首个失败原因）

## 🐛 修复：挑战类徽章永远无法解锁（checkBadges 集合名写错）

**现象**：挑战类里程碑徽章从来没解锁过
**根因**：写入侧与查询侧对不上
- `useChallenge` 写入 `challengeLogs`，字段 `challengerId` / **`opponentId`**
- `checkBadges` 查询 `challengeHistory`，字段 `challengerId` / **`targetId`**

**修复**：改查询侧（`cloudfunctions/checkBadges/index.js` 约 319 行）
```js
const count = await db.collection('challengeLogs')
  .where(_.or([
    { challengerId: studentId },
    { opponentId: studentId }   // 原为 targetId
  ]))
```
**不删** deleteClass/deleteStudent 里的 `challengeHistory` 清理——保留作历史脏数据兜底，无害。

**教训**：集合名/字段名要在**写入侧和查询侧成对核对**，不能只看一边。

## 🐛 WXML 编译错误：`wx:elif/wx:else` 找不到 `wx:if`（character.wxml）

**现象**：「Bad attr `wx:elif`, `wx:if` not found」——字符.wxml 编译失败，页面无法加载

**根因（两个并存）**：
1. `<view>` 上**同时挂了 `wx:else` 和 `wx:for`，并且属性跨多行**。
   WXML 解析器在 `wx:else` 后面找 `wx:if` 时被多行属性搞错位
2. `wx:if` / `wx:elif` 表达式里用了 `===`（全等运算符）。
   WXML 表达式解析器对 `===` / `!==` 兼容性差，部分版本直接拒绝

**修复**：
- 把 `<view wx:else>` 和 `<view wx:for=...>` 合并为单行写法：
  ```xml
  <view wx:else wx:for="{{list}}" wx:key="_id" class="..." bindtap="...">
  ```
- 表达式里的 `===` 改成 `==`（在 WXML 里行为完全一样，零风险）

**校验脚本**：写了一个 Python 校验脚本扫全部 .wxml，列出了**33 处潜在风险点**
（很多是误报，但凡是带 `wx:else` + 多行属性的都建议改成单行）。

**教训**：WXML 里两个「能少折腾就少折腾」的原则
- `wx:if` / `wx:elif` / `wx:else` 链上的 view → 单行写，跨行容易触发误报
- 表达式里的等值判断 → 用 `==` 不用 `===`，省去兼容性烦恼

**WXML 真正硬规则**（踩了 3 次才彻底搞清楚）：
- ❌ `<view wx:else wx:for="{{list}}">` — **绝对不允许**
- ✅ 必须拆成两层：外层 `<view wx:else>`，内层 `<view wx:for="{{list}}">`
- 错误信息是「Bad attr `wx:else` with message: `wx:if not found`」——
  字面意思误导（`wx:if` 明明就在前面），实际是「`wx:else` 后面挂了别的指令」
- `wx:if` / `wx:elif` 也一样：后面不能挂 `wx:for` / `wx:for-item` / `wx:for-index` 等其他指令
- 解法统一：**if/elif/else view 是空壳，只负责条件；指令 view 是内层，负责 wx:for**

**曾踩过的坑**：
1. 第一次改：跨行 `wx:else + wx:for`（误以为是跨行问题）→ 没修好
2. 第二次改：合并成单行 `wx:else wx:for=...`（误以为是单行/多行问题）→ 还是错
3. 第三次改：拆两层 → 终于过

**用户报错时**：开发者工具错误堆栈窗口会自动折行显示，截图里看着像跨行、看着像单行，
**唯一可信的是字节级 Read**——不要被视觉折行误导。

## 🐛 登录页输入框「左留白、右贴边」——`width: 100% + padding` 不带 box-sizing

**现象**：班级密钥/个人密钥两个 input 框左边距 form-area 边缘大、右边几乎贴到屏幕边

**根因**：`.form-area` 写了 `width: 100%` + `padding: 48rpx 40rpx`，**没写 `box-sizing: border-box`**

CSS 默认 `content-box`：
- `width: 100%` = viewport - 96rpx（login-container 自身 padding 48+48）
- padding 80rpx 加在外侧 → form-area 实际占用 = viewport - 16rpx
- 在 flex `align-items: center` 居中后 → 左边距 viewport 8rpx，右边也距 8rpx，但**form-area 的右 padding 已经溢出 viewport**
- input 是 form-area 的内容区子项 → input 右侧被挤到 viewport 边缘附近，左侧留出 form-area 左 padding（40rpx）

**修复**（`miniprogram/pages/login/login.wxss`）：
- `.form-area` 加 `box-sizing: border-box`
- `.input-field` 同时加 `box-sizing: border-box` 和 `display: block`（input 是 inline 元素，`width:100%` 在某些基础库上不生效，display:block 双保险）

**历史教训**：
- 项目里注册弹窗（`.modal-box` / `.modal-input`）原本就有 `box-sizing: border-box`，所以**注册弹窗是对称的**，登录主表单不对衬 → 印证这是「一直以来的遗留问题」
- 顺手扫了全项目 `.wxss`，发现还有 3 处类似风险（`.name-input`/`.question-card`/`.btn-danger`），尚未引发用户反馈但建议有空时一并补上

**WXSS 教训**（写新组件时必须遵守）：
> 任何 `width: 100%`（或 `100vw`）**同时配 padding > 0** 的容器，**必须同时写 `box-sizing: border-box`**
> 否则 padding 会让容器溢出 viewport，造成左右不对称、超出屏幕边界等诡异问题

### `<button>` 微信原生样式的坑（character.wxml 金币资产卡教训）

**症状**：金币资产卡 `.coin-info` 里的"累计获得 0"被挤成竖排（每字一行），同时"明细"按钮被压扁。

**根因（两层叠加）**：

1. **微信 `<button>` 有原生样式 `padding: 0 14px` + `margin: 0 auto` + `box-sizing: border-box`**
   - 每个 button 在 flex 容器中实际占宽 ≈ 120（min-width）+ 28（系统 padding）+ 16（auto margin）= **~164rpx**
   - 远比设计预期 120rpx 多 ~44rpx
   - 两个 button 共抢占 ~88rpx，原本属于 `.coin-info` 的空间
2. **`.coin-info` 缺 `flex: 1`**，只设了 `display:flex; flex-direction:column; min-width:0`
   - 在 flex 容器内 grow=0，无法主动抢占空间
   - 一旦被 button 系统样式挤到 < 单字符 22rpx，"累计获得 0"就每字换行

**修复模板**（写任何嵌入 flex 容器中段、且会"挤"邻居的 button 都得这样写）：

```css
.btn-in-flex {
  box-sizing: border-box;
  padding: 0 24rpx !important;   /* !important 覆盖系统 padding: 0 14px */
  margin: 0 !important;          /* !important 覆盖系统 margin: 0 auto */
  flex-shrink: 0;                /* 防被 flex 容器压缩 */
  /* 父容器（容纳 button 的 flex 容器）必须设 min-width 保底，
     否则 button 的 auto margin 会无限扩张 */
}
.parent {
  display: flex;
  flex-shrink: 0;
  min-width: button_min * count + gap * (count-1) + 8;  /* +8rpx 缓冲 */
}

/* 关键：被 button 挤压的弹性子项必须显式 flex:1 */
.info {
  flex: 1;
  min-width: 0;
  overflow: hidden;
}
.info-sub {
  white-space: nowrap;            /* 防再被压成竖排 */
  overflow: hidden;
  text-overflow: ellipsis;
}
```

**已有的同类 button**（暂未触发用户反馈，但有同款风险）：
- `character.wxss .checkin-btn`（padding 16/32，没 box-sizing，没 !important）—— 风险低，因为 .checkin-card 结构简单，button 在右端独立，没挤压邻居
- 未来若写「嵌入式按钮组」（button 在 flex 容器中间，左右都有内容），**必须按上述模板**写

**WXML `<button>` 已知默认样式**（与浏览器 button 行为不同）：
- `padding-left/right: 14px`
- `margin-left/right: auto`（**flex 容器中会强制两端对齐**）
- `box-sizing: border-box`（原生默认就是 border-box）
- `font-size: 18px`（比正文 16px 略大）
- `::after` 伪元素有 1px 边框（**必须写 `::after { border: none }` 才能去掉**）
- `line-height: 1.4`（不能直接用 height 锁死，要配合 line-height）

## placeholder 自渲染第二轮坑（2026-09-01 第四轮）

**新症状**：第三轮实施后用户反馈「字全了，但跑到输入框外面了」——「输入班级密钥」左端起点在框内，但「钥」字明显伸出 input 右边界。

**根因**：`.ph` 用了 `<text>` 元素，而微信 `<text>` 默认 `display: inline`。
- inline 元素上：`overflow: hidden` + `text-overflow: ellipsis` + `max-width` 全部失效
- 文字宽度 = 内容自然宽度，绝对定位的 `left: 28rpx` 只锁了左边，右边直接撑出去
- `max-width: calc(100% - 56rpx)` 没用——因为 inline 容器不算 box

**修法（必须三件套）**：
```css
.ph {
  display: block;           /* 关键：否则后面规则全部失效 */
  position: absolute;
  left: 28rpx;
  right: 28rpx;             /* 用 right 锁定右边，比 max-width 更稳 */
  ...
  white-space: nowrap;
  overflow: hidden;
  text-overflow: ellipsis;
}
```

**三件套缺一不可**：
1. `display:block` —— 让 `<text>` 当 box 元素
2. `left + right`（非 `max-width`）—— 锁住宽度
3. `white-space:nowrap + overflow:hidden + text-overflow:ellipsis` —— 真正截断

**全项目 9 处 `.ph` selectors 全部修复**（含 `.ph-textarea`，同样加 block + right）：
- login.wxss / teacher-class.wxss / character.wxss / create-character.wxss / teacher-task.wxss（.ph + 2× .ph-textarea）
- teacher-score.wxss（.ph-amount + .ph-search）

**校验**：grep `max-width: calc(100%` 残留 = 0；`display:block` 在 6 个 wxss 的 .ph 上全部命中；标签平衡 0 违规。

**教训追加到 MEMORY.md 第 4 条**：自渲染 `<text>` 默认 inline，CSS **必须 display:block**。
- 之前踩过「WXSS 元素要 box-sizing 必须显式」同一类坑——webkit/webview 上 inline 默认值与直觉相反

## 金币资产卡第三次修复（2026-09-01）

**症状**：character 页"金币资产卡"用户反馈"看不到金额、按钮太大平铺"。
截图显示两个按钮（明细、赠送）几乎平分整个卡片，金额数字与累计获得完全不可见。

**根因**：`.coin-btn` 单设 `min-width: 120rpx; padding: 0 24rpx !important;` 不够——
- 按钮在 `.coin-actions` (display:flex) 内是 flex items
- 默认 flex-basis: auto + flex-grow: 0，按内容宽度算 basis
- 但**当容器内有剩余空间时，flex 会把剩余空间平分给所有可增长子项** →
  按钮实际宽度 ≈ (容器宽 - gap) / 2，远大于 120rpx
- 加 `min-width` 仅设下限，无法阻止扩张

**修法四件套**：对每个 flex item 都设死宽度（width + min-width + max-width + flex: 0 0 N）

```css
.coin-actions { width: 256rpx; flex-shrink: 0; }
.coin-actions .coin-btn {
  flex: 0 0 118rpx !important;
  width: 118rpx !important; min-width: 118rpx !important; max-width: 118rpx !important;
  padding: 0 !important;  /* 不写 padding，避免 box-sizing 不一致 */
  text-align: center;
  height: 56rpx; line-height: 56rpx;
}
```
`.coin-left { flex: 1; min-width: 0; margin-right: 20rpx; }` 拿剩余空间。

**为什么之前没发现**：
