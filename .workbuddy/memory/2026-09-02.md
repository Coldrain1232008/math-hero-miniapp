## 密钥鉴权审计（commit 029ab63 + c00d625）

### 事故：teacher-shop 商城管理页恒弹「教师密钥不正确」
- 根因：`login.findByKey` 双查（raw→upper）兼容历史小写密钥，登录成功；
  但 `manageShop.verifyTeacher` 只查归一化后的 upper → 小写历史密钥查不到
- 修法：manageShop / superAdmin 的鉴权函数改双查（与 login 一致）
- 教训升华：不是「归一化要成对」，而是**所有密钥查询函数都该双查**。
  每新增一个需鉴权的云函数，不能照抄单查，必须复用双查模式

### 决定：不抽公共模块，改成自动检测
用户授权我决定。判断依据：
- 抽 `cloudfunctions/common/findByKey.js` 要求每个云函数上传时带 common 目录，
  微信云函数默认不上传上层目录，部署方式要改，成本 > 收益
- 真正的风险是「忘记做双查」，靠人记不靠谱 → 做成检测脚本

### 产出：`tools/check-auth.js`（两维度）
- 维度一 密钥双查：识别字面量键、动态键（`where({[field]:raw})`）、
  泛型函数（`login.findByKey`）三种写法；区分鉴权/查重用途（避免误报）
- 维度二 写操作鉴权：三档分级
  🔴 写 + event 收 classId + 无密钥 = 可跨班写入
  ⚠️  写 + event 收 studentId + 无密钥/openid = 可操作同班他人
- **负向测试**：造假云函数验证脚本能报 🔴（脚本自身要能防回归）

### 顺带挖出的重大漏洞（比密钥大小写严重得多）

1. `.remove()` 常不带参数直接跟在 `.where()` 后面，原正则要求后面必须

2. 「已鉴权」原判据是「出现 teacherKey + where()」 → teacherGrantItem

## 收尾：豁免机制 + 写入侧归一化（同日续）

### 启发式脚本必然有误报 → 加「人工豁免签名」
正则扫描看不出「值在上游已归一化」这类上下文，与其不断堆判定规则，
不如让开发者显式签名。check-auth.js 支持 `// auth-ok: 理由`：
- 位置：where 行尾 / 上一行 / 下一行（链式调用注释常写在链首行尾）
- 脚本仍列出这些行并标 ✅ 已豁免，**不静默跳过**——豁免是签名不是删除

实现踩坑：向上查找时最初要求「整行是注释」（`t.startsWith('//')`），
行尾注释被漏掉 → 改成直接 `EXEMPT_RE.test(lines[k])`。

已豁免 3 处：importStudents ×2（studentKey 上游已归一化）、
updateClassKeys ×1（查重，key 由 KEY_REG 保证大写）。
维度一 🔴 归零，只剩 createClass 的 ⚠️（建班查重，低危）。

### 负向测试是豁免机制的配套
加豁免后必须验证检测能力没被关掉：造 `__authprobe` 假函数 →
两个维度都报警、退出码 1；`rm -rf` 后退出码 0。**每次改判定规则都要重跑**。
